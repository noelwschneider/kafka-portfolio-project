# Event Catalog

**Status:** frozen by Phase 0. This file is the single source of truth for event names, the event
envelope, topic assignment, and publisher/consumer relationships. Any workstream that needs a change
here must follow the coordination protocol in `docs/planning/engineering-rules.md`'s Agent Coordination
Rules section (propose the change in this file first, state why, then update implementations and
tests) — not work around it locally.

Draft source: `docs/planning/sprint-1/backend-design.md`'s Event Design, Kafka Topic Strategy, and
Event-Driven Order Lifecycle sections.

JSON Schema files for each payload (`docs/events/schemas/*.json`) are deliberately **not** part of
Phase 0 — `docs/planning/sprint-1/execution-plan.md` §7 places them at Phase 2, once payloads have been
exercised by real producers and consumers.

---

## 1. Envelope

Every domain event uses the same envelope. Consumers deserialize the envelope first, then the
`payload` according to `eventType` + `eventVersion`.

```json
{
  "eventId": "0c7c3acd-8b3b-45fd-ae4a-b8c73b5a419e",
  "eventType": "OrderCreated",
  "eventVersion": 1,
  "occurredAt": "2026-08-07T20:31:04.220Z",
  "correlationId": "d89512f7-b544-4170-b66b-2e93f475ea8f",
  "aggregateId": "order-21873",
  "payload": {
    "orderId": "order-21873",
    "customerId": "demo-customer",
    "items": [
      {
        "sku": "SKU-001",
        "quantity": 2
      }
    ]
  }
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `eventId` | string (UUID v4) | yes | Unique per **published record**. The idempotency key for consumers — see `processed_events` in `docs/db-ownership.md`. A duplicate delivery of the same logical event reuses the same `eventId` (that is exactly what Scenario 4 republishes). |
| `eventType` | string | yes | One of the names in §3. Used for routing and for `payload` interpretation. |
| `eventVersion` | integer | yes | Starts at `1` for every event type. See §5 for the versioning rule. |
| `occurredAt` | string (RFC 3339, UTC, millisecond precision) | yes | When the publishing service decided the event happened — not when it was written to Kafka. |
| `correlationId` | string (UUID v4) | yes | Constant for all events belonging to one logical workflow (one order, or one scenario run). Generated by whichever component starts the workflow (Order Service on `POST /api/orders`, Scenario Service on a scenario run) and copied by every consumer onto every event it publishes in reaction. |
| `aggregateId` | string | yes | The aggregate the event is about. For every event in this catalog this is the `orderId`, and it is also the Kafka record key (§2). |
| `payload` | object | yes | Event-type-specific. Never null; use `{}` rather than omitting. |

Envelope fields are **not** repeated inside `payload`, with one deliberate exception: `orderId`
appears in both `aggregateId` and each payload, because payload consumers should not have to
understand the envelope's aggregate convention to find the order.

## 2. Topics and keys

Topics are domain-oriented, per `docs/planning/sprint-1/backend-design.md`'s Kafka Topic Strategy section.

**Frozen rule: a service publishes only to its own domain topic.** Consumers subscribe to whichever
topics carry the events they need. This is why `PaymentRequested` — a payment-domain event, but
published by Order Service — lives on `orders.events` and not on `payments.events`: the alternative
would make Payment Service both a producer and a consumer of the same topic, so every Payment
Service consumer would have to filter out its own output.

| Topic | Published by | Carries |
|---|---|---|
| `orders.events` | Order Service | `OrderCreated`, `PaymentRequested` |
| `inventory.events` | Inventory Service | `InventoryReserved`, `InventoryReservationFailed`, `InventoryReleased` |
| `payments.events` | Payment Service | `PaymentAuthorized`, `PaymentRejected` |
| `fulfillment.events` | Fulfillment Service | `ShipmentCreated` |
| `demo.events` | Scenario Service | Scenario-run lifecycle records used to build the run timeline. Not domain events; no entry in §3. |
| `orders.dlq`, `inventory.dlq`, `payments.dlq`, `fulfillment.dlq` | the failing **consumer** | Records that exhausted retries, plus failure metadata. Routing targets, not domain event types. |

**Record key = `aggregateId` = `orderId`** on every topic. This gives per-order ordering within a
partition, which is the property the workflow actually depends on (an order's `InventoryReserved`
must not be processed after its `PaymentAuthorized`). It provides no cross-order ordering, and the
implementation must not assume any.

### Delivery semantics

At-least-once. Consumers must tolerate duplicate delivery and are made idempotent via the
`processed_events` check described in `docs/planning/sprint-1/backend-design.md`'s Idempotent consumers
section. This project does **not** implement exactly-once semantics, and no document, UI string, or
README may claim it.

Until Phase 6 (transactional outbox), publishers persist their business change and then publish —
so a crash between commit and publish loses the event. That window is a known, documented
limitation; see `docs/adr/ADR-006-transactional-outbox-for-db-kafka-consistency.md`.

## 3. Events

All events are at `eventVersion: 1`.

### `OrderCreated`

| | |
|---|---|
| **Published by** | Order Service |
| **Consumed by** | Inventory Service |
| **Topic** | `orders.events` |
| **Trigger** | A `POST /api/orders` request passed validation and the order was persisted with status `PENDING`. |
| **Order status effect** | None. The order is already `PENDING` when this is published; publication is part of entering `PENDING`, not a transition out of it. |

```json
{
  "orderId": "order-21873",
  "customerId": "demo-customer",
  "items": [
    { "sku": "SKU-001", "quantity": 2 }
  ]
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `customerId` | string | yes |
| `items[].sku` | string | yes |
| `items[].quantity` | integer ≥ 1 | yes |

No prices here: the only consumer is Inventory Service, which has no use for them. The order amount
travels on `PaymentRequested` instead.

---

### `InventoryReserved`

| | |
|---|---|
| **Published by** | Inventory Service |
| **Consumed by** | Order Service |
| **Topic** | `inventory.events` |
| **Trigger** | Every line of an `OrderCreated` order was successfully reserved against available stock, in one transaction. |
| **Order status effect** | `PENDING` → `INVENTORY_RESERVED` |

```json
{
  "orderId": "order-21873",
  "reservationId": "resv-4471",
  "items": [
    { "sku": "SKU-001", "quantity": 2 }
  ],
  "reservedAt": "2026-08-07T20:31:04.251Z"
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `reservationId` | string | yes |
| `items[].sku` | string | yes |
| `items[].quantity` | integer ≥ 1 | yes |
| `reservedAt` | string (RFC 3339) | yes |

Reservation is all-or-nothing per order: a partially satisfiable order publishes
`InventoryReservationFailed`, never `InventoryReserved` for a subset of lines.

---

### `InventoryReservationFailed`

| | |
|---|---|
| **Published by** | Inventory Service |
| **Consumed by** | Order Service |
| **Topic** | `inventory.events` |
| **Trigger** | At least one line of an `OrderCreated` order cannot be satisfied from available stock. |
| **Order status effect** | `PENDING` → `REJECTED_OUT_OF_STOCK` (terminal) |

```json
{
  "orderId": "order-21873",
  "reason": "INSUFFICIENT_STOCK",
  "shortages": [
    { "sku": "SKU-004", "requested": 2, "available": 0 }
  ]
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `reason` | string enum: `INSUFFICIENT_STOCK`, `UNKNOWN_SKU` | yes |
| `shortages[].sku` | string | yes |
| `shortages[].requested` | integer | yes |
| `shortages[].available` | integer | yes |

This is a **business rejection**, not an error: it is the expected outcome of Scenario 2 and of the
losing order in Scenario 7. It is never retried and never dead-lettered.

---

### `InventoryReleased`

| | |
|---|---|
| **Published by** | Inventory Service |
| **Consumed by** | No service in v1 — consumed only by the scenario-run timeline / UI |
| **Topic** | `inventory.events` |
| **Trigger** | A reservation was released as compensation, after Inventory Service consumed `PaymentRejected`. |
| **Order status effect** | None. The order is already `PAYMENT_FAILED`; releasing stock does not move it. |

```json
{
  "orderId": "order-21873",
  "reservationId": "resv-4471",
  "items": [
    { "sku": "SKU-001", "quantity": 2 }
  ],
  "reason": "PAYMENT_REJECTED",
  "releasedAt": "2026-08-07T20:31:05.104Z"
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `reservationId` | string | yes |
| `items[].sku` | string | yes |
| `items[].quantity` | integer ≥ 1 | yes |
| `reason` | string enum: `PAYMENT_REJECTED` | yes |
| `releasedAt` | string (RFC 3339) | yes |

**Judgment call (Phase 0):** this event is not named anywhere in the planning docs. It exists
because `docs/planning/sprint-1/frontend-design.md`'s Scenario 3 advertises "compensation, inventory release"
as something the scenario *demonstrates* — and a release that publishes nothing is invisible in the
run timeline, which would make the demo unable to show its own headline behavior. It has no
subscriber in v1 by design; adding one later does not change the event.

---

### `PaymentRequested`

| | |
|---|---|
| **Published by** | Order Service |
| **Consumed by** | Payment Service |
| **Topic** | `orders.events` |
| **Trigger** | Order Service consumed `InventoryReserved` and is asking for authorization. |
| **Order status effect** | `INVENTORY_RESERVED` → `PAYMENT_PENDING`. The transition and the publication happen in the same Order Service transaction. |

```json
{
  "orderId": "order-21873",
  "amount": 258.00,
  "idempotencyKey": "3f1a8c02-5f8e-4a2b-9d77-0b41c2f9e6aa"
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `amount` | number (2 decimal places) | yes |
| `idempotencyKey` | string (UUID v4) | yes |

`amount` is `orders.total_amount`, computed by Order Service at creation time from its seeded SKU
price map (see `docs/db-ownership.md`, "Where prices come from"). There is no currency field: the
whole project uses one implicit currency.

`idempotencyKey` is the `eventId` of this `PaymentRequested` event. It is stored as
`payment_attempts.idempotency_key`, so a redelivery of the same event maps to the same attempt row
rather than authorizing twice.

**Judgment call (Phase 0):** `docs/planning/sprint-1/backend-design.md`'s lifecycle diagram attributes this
event to "Order Service / Payment workflow", which is ambiguous. Frozen as **Order Service**, since
that is what makes `PAYMENT_PENDING` a reachable order state and keeps payment authorization from
depending on Payment Service watching inventory events.

---

### `PaymentAuthorized`

| | |
|---|---|
| **Published by** | Payment Service |
| **Consumed by** | Order Service, Fulfillment Service |
| **Topic** | `payments.events` |
| **Trigger** | The payment simulator authorized the requested amount. |
| **Order status effect** | `PAYMENT_PENDING` → `PAID`, then the internal `PAID` → `FULFILLMENT_PENDING` step in the same handler (see `docs/order-state-machine.md`). |

```json
{
  "orderId": "order-21873",
  "paymentAttemptId": "pay-9932",
  "amount": 258.00,
  "authorizedAt": "2026-08-07T20:31:04.361Z"
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `paymentAttemptId` | string | yes |
| `amount` | number (2 decimal places) | yes |
| `authorizedAt` | string (RFC 3339) | yes |

This is the project's one fan-out event: two services consume it independently, in separate consumer
groups, for different reasons (Order Service updates lifecycle state; Fulfillment Service creates a
shipment). Neither waits for the other.

---

### `PaymentRejected`

| | |
|---|---|
| **Published by** | Payment Service |
| **Consumed by** | Order Service, Inventory Service |
| **Topic** | `payments.events` |
| **Trigger** | The payment simulator declined authorization — a non-retryable business outcome. |
| **Order status effect** | `PAYMENT_PENDING` → `PAYMENT_FAILED` (terminal) |

```json
{
  "orderId": "order-21873",
  "paymentAttemptId": "pay-9932",
  "amount": 258.00,
  "failureReason": "CARD_DECLINED",
  "rejectedAt": "2026-08-07T20:31:04.377Z"
}
```

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `paymentAttemptId` | string | yes |
| `amount` | number (2 decimal places) | yes |
| `failureReason` | string enum: `CARD_DECLINED`, `INSUFFICIENT_FUNDS` | yes |
| `rejectedAt` | string (RFC 3339) | yes |

Inventory Service's subscription to this event is the compensation trigger: it releases the order's
reservation and publishes `InventoryReleased`.

`PaymentRejected` means *the payment was declined*. A **retryable** simulated provider error
(`docs/planning/sprint-1/backend-design.md` 4.3) is a different thing: it raises inside the Payment Service
consumer, is retried with backoff, and lands in `payments.dlq` if attempts are exhausted. It never
surfaces as `PaymentRejected`, and it leaves the order in `PAYMENT_PENDING`.

| Payload field | Type | Required |
|---|---|---|
| `orderId` | string | yes |
| `shipmentId` | string | yes |
| `trackingNumber` | string | yes |
| `createdAt` | string (RFC 3339) | yes |

`trackingNumber` is generated locally; nothing in this project talks to a carrier.

## 4. Events considered and deliberately excluded from v1

| Candidate | Source | Why excluded |
|---|---|---|
| `OrderShipped` | `docs/planning/sprint-1/backend-design.md` 4.4, listed as an "optional later event" | In v1 a shipment is created and the order is immediately `FULFILLED`; there is no separate physical dispatch step to report, so the event would carry no information `ShipmentCreated` doesn't. Revisit if a shipment ever acquires a lifecycle of its own. |
| `FulfillmentRequested` | Not in the planning docs; considered while formalizing the state machine | It would make `PAID` → `FULFILLMENT_PENDING` event-driven and mirror `PaymentRequested` nicely, but `docs/planning/sprint-1/backend-design.md` 4.4 explicitly specifies that Fulfillment Service **consumes `PaymentAuthorized`**. Adding it would contradict a frozen design doc for a cosmetic gain. |
| Notification events | `docs/planning/sprint-1/backend-design.md` 4.5 (optional Notification Service) | That service is explicitly "only add this after the core system is stable". No service publishes or consumes notification events in v1. |

## 5. Versioning rule

`eventVersion` is per event type and starts at `1`.

- **Additive, optional payload field** → no version bump. Consumers must ignore unknown fields, so
  deserialization is configured to tolerate them.
- **New required field, removed field, renamed field, or changed field semantics** → bump
  `eventVersion` for that event type only, and add a row to the event's section here describing what
  changed between versions.
- A consumer that receives an `eventVersion` it does not know must treat it as a **non-retryable**
  failure and route the record to its DLQ. Retrying cannot fix a schema it doesn't understand.

`eventVersion` exists in v1 mainly so that this rule can be stated and demonstrated; no event is
expected to reach version 2 during the initial build.
